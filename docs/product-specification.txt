Build a full-stack notes application named MindKeep.

Treat this specification as the agreed product scope. Implement the selected features faithfully and keep the interface focused on quick note capture.

1. PRODUCT PURPOSE

MindKeep helps everyday users write something down before they forget it.

Typical uses include:
- Saving a sudden idea.
- Recording a shopping list.
- Remembering an errand.
- Keeping an important personal detail.
- Recording a quick voice note.
- Setting a reminder to revisit something.

The central experience is:
Open the app → capture a note → save automatically → find it again when needed.

MindKeep should feel simple, calm, welcoming, and fast.

It is an everyday notes application. Do not introduce study tools, flashcards, AI assistants, project-management dashboards, databases of custom properties, or complex workspace systems.

Google Keep is the reference for the general interface structure and familiar note interactions. Use MindKeep’s own branding, colors, styling, and selected features.

The approved design direction is “Airy Cards,” with a slightly stronger blue influence.

2. TECHNOLOGY AND ARCHITECTURE

Use:
- C++ for the backend and the search engine.
- HTML, CSS, and JavaScript for the frontend.
- MySQL for persistent structured data.
- CMake for the C++ build.

Prefer C++20 where supported by the development environment.

A suitable C++ web framework and supporting libraries may be used. Choose dependencies based on maintainability and compatibility, and explain the choices in the documentation.

The frontend may use a suitable JavaScript framework, but keep the architecture understandable and avoid unnecessary complexity.

A rich-text editor library is allowed. Configure it to provide only the selected editing capabilities.

All authoritative backend operations must run through the C++ backend, including:
- Authentication and authorization.
- Note persistence.
- Search and search filtering.
- Folder and tag management.
- Attachment ownership and access.
- Sharing permissions.
- Synchronization.
- Reminder scheduling.

Do not substitute another backend language for C++.

MySQL is the persistent source of truth. The custom C++ search index is a derived structure that can be rebuilt from stored notes.

Images and audio may use file storage, with their ownership, storage references, and metadata stored in MySQL.

7. C++ SEARCH ENGINE

Build the primary search engine yourself using appropriate C++ data structures.

Do not use:
- MySQL full-text search as the main search engine.
- Elasticsearch.
- A hosted search service.
- A library that replaces the project’s indexing and retrieval algorithms.

Supporting libraries for Unicode processing, parsing, and other low-level concerns are allowed.

REQUIRED STRUCTURES

Use and justify an appropriate combination of:

- Hash maps for term dictionaries and direct lookups.
- An inverted index mapping terms to matching note IDs.
- Posting lists containing term frequencies and token positions.
- A trie or another justified structure for title-prefix search.
- Appropriate structures for folder, tag, and date filtering.
- Set operations for combining matching note IDs.

Keep title and body information separate so ranking can treat them differently.

TEXT PROCESSING

Implement:
- Extraction of searchable text from rich-text content.
- Consistent tokenization.
- Case normalization.
- Defined punctuation handling.
- Correct treatment of UTF-8 input.
- Stable token positions for phrase matching.

If stop words are removed for ranking, preserve the information needed for accurate phrase matching.

Do not index raw HTML markup as visible note content.

SEARCH BEHAVIOR

Support:
- Title search.
- Full-content search.
- Title-prefix matching.
- Exact quoted phrases using token positions.
- Selected filters.
- Saved searches.
- Useful result snippets.
- Highlighted matches.

Define and document how ordinary multiword searches are interpreted.

Parse advanced search syntax deliberately. Handle invalid syntax with a clear message rather than silently changing its meaning.

Support quoted values where appropriate, for example:
tag:“Personal Ideas”

Define whether before: and after: apply to creation or modification dates, and show that meaning in the interface and documentation.

RANKING

Use a documented ranking method.

At minimum:
- Give title matches greater weight than body matches.
- Account for term relevance or frequency.
- Use a deterministic tie-breaker.
- Explain the scoring approach in the project report.

INDEX LIFECYCLE

Update the index after:
- Note creation.
- Content or title edits.
- Deletion and permanent deletion.
- Restoration.
- Changes that affect filters.

Manage database persistence and index updates in a controlled lifecycle.

Rebuild the index after a server restart.

Use concurrency controls so searches cannot read corrupted index structures during updates.

USER ISOLATION

Scope every private search to the authenticated user.

Do not expose another user’s:
- Titles.
- Content.
- Tags.
- Attachments.
- Search snippets.
- Result counts that reveal private data.

Locked-note titles, content, and snippets must follow the chosen privacy policy. Do not expose protected content without the required unlock.

Archived and trashed notes must have predictable search behavior. Default searches should exclude Trash.

DOCUMENTATION AND EVALUATION

Document:
- Data structures.
- Index construction.
- Query processing.
- Phrase matching.
- Filtering.
- Ranking.
- Index updates.
- Time and space complexity.
- Memory and concurrency considerations.

Provide meaningful tests for:
- Tokenization.
- Phrase matching.
- Ranking.
- Filtering.
- Updates and deletions.
- Rebuilding the index.
- User isolation.
- Locked-note visibility.

Include reproducible performance measurements on generated datasets of increasing size.

Measure indexing time, search latency, and approximate index memory use. Report observed results honestly.

8. AUTOSAVE AND OFFLINE BEHAVIOR

AUTOSAVE

Use a short debounce suitable for typing, such as approximately 500–1000ms.

Preserve local drafts immediately enough to protect against accidental navigation.

Display distinct states:
- Saving.
- Saved.
- Saved on this device.
- Waiting to sync.
- Unable to save.

Do not display “Saved” as confirmation of server persistence before the server acknowledges it.

Retry recoverable failures without creating duplicate notes.

OFFLINE SUPPORT

Use appropriate browser storage for offline notes and pending operations.

Cache the application resources needed for the offline writing experience.

Allow users with an established local account session to create and edit notes offline.

Clearly identify actions that require a connection.

Do not persist session secrets unnecessarily or allow offline storage to bypass note locks.

Protect locally stored private content according to the lock design and document the security boundaries.

SYNCHRONIZATION

Use stable IDs and revision information.

Support:
- Uploading pending local changes.
- Receiving changes made on another device.
- Synchronizing deletion and restoration.
- Synchronizing relevant attachment metadata and uploads.
- Retrying safely.

Detect concurrent edits.

Preserve both versions when a conflict cannot be merged safely. Give the user a clear way to resolve it.

Never silently overwrite a user’s unsynchronized work.

Keep timestamps internally consistent and display dates in the user’s local timezone.

9. ACCOUNTS, LOCKS, AND SHARING

AUTHENTICATION

Use:
- Secure password hashing.
- Parameterized database queries.
- Server-side authorization.
- Appropriate session expiry.
- Secure cookie settings where applicable.
- Protection against relevant request and content-injection attacks.

Do not store plaintext passwords.

PASSWORD RESET

Implement:
- A reset request.
- A securely generated reset token.
- Expiry and single-use enforcement.
- Password replacement.
- Appropriate invalidation of affected sessions.

Document email-delivery configuration.

A mocked email or console token must not be presented as a completed production reset flow.

APP LOCK

Manual or inactivity locking must hide private content and require verification before access resumes.

Do not implement app lock only as a cosmetic overlay that can be bypassed through ordinary backend requests.

NOTE LOCKS

Enforce locked-note access on the backend.

Check attachments, exports, search snippets, and sharing routes as well as the editor.

Do not claim end-to-end encryption unless it is actually implemented; it is not a selected feature.

READ-ONLY SHARING

Generate unguessable sharing tokens.

Expose only the selected note and authorized media.

Do not expose account information or unrelated notes.

Require explicit owner authorization to share a locked note.

Revoke access when the owner revokes the link or when the note’s deletion state requires it.

12. EXPORT, BACKUP, AND RESTORE

EXPORT

Provide actual outputs for:
- Plain text.
- Markdown.
- HTML.
- PDF.

Preserve the formatting supported by each format.

Define how images and audio are represented.

PDF output must handle long notes, page breaks, lists, and supported characters.

Do not present an HTML file renamed with a .pdf extension as PDF export.

Enforce ownership and unlock requirements before export.

BACKUP

Create a portable, versioned backup containing the user’s notes, organization metadata, reminders, and required attachment files.

Do not include passwords, session tokens, reset tokens, or reusable private sharing credentials.

RESTORE

Validate the backup before importing.

Handle malformed or incompatible files safely.

Preserve existing notes unless the user explicitly chooses a replacement operation.

Prevent accidental ID collisions and cross-account ownership.

Report what was restored and any items that could not be restored.
